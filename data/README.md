# TraceDeck demo events

`events.json` contains 100 synthetic events: 20 requests with five events each,
across web-gateway, auth-service, checkout-service, and payment-service.
Fourteen requests succeed and six fail: 82 INFO, 6 WARN, and 12 ERROR events.
The UTC range is 2026-09-20 14:00:00 through 14:19:04. Requests start one minute
apart and their events are one second apart. A failed request does not establish
that an entire service is down. No real services or personal data are involved.

## Import using the frontend

1. Close any investigation drawer and find Import events.
2. Click Download 100-event dataset, or select `data/events.json` directly.
3. Choose the file, then click Import events. Expect 100 imported events.
4. Filters clear and the table returns to page 1.

Import appends; it does not replace or deduplicate. Five preexisting events plus
one import means 105 total events and six pages of 20. The fixture itself has
exactly 100 events. Importing it again reuses request IDs and can mix repeated
copies into context history, so import once for a clean demonstration.

## Failure traces

All times below are UTC on 2026-09-20. Select the final event to see four earlier
events plus the selected event. The heuristic is the earliest warning in that
window; it is not a proven root cause.

- `req-demo-1003`: expired token. REQUEST_REJECTED at 14:02:04.
  Expected heuristic: TOKEN_EXPIRING.
- `req-demo-1006`: missing cart item. CHECKOUT_REJECTED at 14:05:04.
  Expected heuristic: CART_ITEM_UNAVAILABLE.
- `req-demo-1009`: payment timeout. CHECKOUT_FAILED at 14:08:04.
  Expected heuristic: PAYMENT_PROVIDER_SLOW.
- `req-demo-1012`: unsupported postal code. CHECKOUT_REJECTED at 14:11:04.
  Expected heuristic: POSTAL_CODE_UNSUPPORTED.
- `req-demo-1015`: database connection failure. CHECKOUT_FAILED at 14:14:04.
  Expected heuristic: DB_POOL_EXHAUSTED.
- `req-demo-1018`: payment declined. CHECKOUT_FAILED at 14:17:04.
  Expected heuristic: PAYMENT_RISK_REVIEW.

For a focused demo, filter checkout-service from 14:08:00 through 14:08:04 UTC
and investigate CHECKOUT_FAILED for req-demo-1009. Its context includes the other
services despite that filter. To select PAYMENT_TIMEOUT itself, use
payment-service in the same range; context then ends at that timeout.

For a successful trace, investigate CHECKOUT_COMPLETED for req-demo-1020 at
14:19:04 UTC. Expect five INFO events and no probable-cause suggestion.

## Reproduce and verify

From the repository root, run `node data/generate-events.mjs`. The generator uses
fixed scenarios and readable loops to write `data/events.json` and the identical
download `frontend/public/demo-events.json`. Edit the generator rather than its
generated output. Generation does not write to PostgreSQL. Input data is
deterministic; event UUIDs are generated by the backend at import time.

From `frontend`, run `npm test` and `npm run build`. Dataset tests verify matching
generated copies, counts, ordering, six expected failure heuristics, successful
traces, and import field constraints. Details are JSON text, not JSONB.
